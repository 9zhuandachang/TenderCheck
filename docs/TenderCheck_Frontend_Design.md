# TenderCheck 前端设计方案（Proposal 交付版）

日期：2026-10-19  
版本：v2.0  
用途：统一页面设计、划分前后端工作、制定排期和验收用例。  
依据：[项目 Proposal](TenderCheck_Project_Proposal.pptx)

本方案以 Proposal 承诺的原型为交付目标，按 Must／Should／Won't 划分范围。表中“出处”一列指向 Proposal 的对应页，用于核对每项功能是否属于承诺范围。超出 Proposal 的能力列入第 9 节，作为报告中的 Future Work。

## 1. 交付目标与范围

TenderCheck 是证据驱动的投标合规审查原型。用户上传招标、补遗和投标 PDF，系统识别要求并自动核验，用户在双栏界面中核对证据，对问题进行整改和复检，最后签核并导出合规矩阵。

| 范围项 | 本期目标 | 出处 | 优先级 |
| --- | --- | --- | --- |
| 输入 | 招标、补遗／澄清、投标 PDF | P3 | Must |
| 文档限制 | 可搜索英文 PDF，每个文档包最多 100 页 | P3 | Must |
| 要求识别 | 要求提取与条款分类，可人工纠正 | P4、P5 | Must |
| 自动审查 | 证据检索、结构化抽取、显式规则核验 | P4、P5 | Must |
| 歧义处理 | 证据不足或有歧义时转人工，不直接判定不符合 | P4 | Must |
| 证据审阅 | 招标与投标证据并排显示，带页码引用 | P3 | Must |
| 版本检查 | 补遗对要求的修改、图纸登记与版本冲突检查 | P3、P5 | Must |
| 整改闭环 | 静态知识库建议、修订草稿、上传新版本、复检 | P3、P4、P5 | Must |
| 交付 | 签核、导出合规矩阵 | P3、P5 | Must |
| 验证支撑 | 历史案例回放、人工审查用时记录 | P2、P6 | Should |
| 保密风险 | LLM 外发提示、项目数据删除 | P7 | Must（提示与删除） |
| 技术栈 | Streamlit 双栏工作台 | P8 | Must |

界面语言以英文为主，与英文输入文档和课程演示保持一致。本文档用中文书写，界面文案在实现时统一为英文。

## 2. 用户与流程

Proposal 的主要用户分为两类，本期用角色区分各自的主要操作，不做账号权限控制：

| 角色 | 主要操作 |
| --- | --- |
| Reviewer（投标协调员／工程师） | 上传文件、确认要求、核对证据、整改与复检 |
| Manager（投标／估算经理） | 查看概览与未决项、签核、导出 |

用户进入项目时选择角色，概览页按角色显示待办，签核记录中写入签核人。

主流程与 Proposal 的五步对应：

| Proposal 步骤 | 页面 |
| --- | --- |
| 01 Upload Documents | 文档与版本 |
| 02 Automated Inspection | 要求清单 → 启动审查 |
| 03 Review & Trace Evidence | 审查工作台 |
| 04 Remediate & Re-inspect | 整改与复检（含知识库） |
| 05 Sign-off & Export | 报告与签核 |

要求通过核验（pass）后等待签核；发现冲突（conflict）进入整改；修改投标文件（modify）后上传新版本，再次检查（re-inspect）形成新一轮审查。每轮结果都保留，供复检对比。

应用共六个页面，项目概览作为入口：

| 页面 | 主要任务 | 核心操作 |
| --- | --- | --- |
| Overview | 查看进度和待办 | 继续审查、进入问题列表 |
| Documents | 管理输入文件、补遗和图纸 | 上传、查看解析状态、图纸登记检查 |
| Requirements | 确认待审查的要求 | 查看来源、纠正类别与字段、标记不适用 |
| Review Workspace | 逐条核对证据 | 筛选、定位原文、确认或纠正、转入整改 |
| Remediation | 整改并复检 | 查看知识库建议、编辑草稿、上传新版本、复检对比 |
| Report | 签核和交付 | 查看矩阵与未决项、签核、导出、评估视图 |

切换页面时保留当前项目、审查轮次、筛选条件和正在处理的条款。

## 3. 页面设计

### 3.1 Overview

显示项目名称、当前投标版本、审查轮次和处理进度。四个统计卡片为：待复核、不符合、证据不足、待整改，点击后进入审查工作台并带上对应筛选条件。

系统处理进度和人工复核进度分开显示，例如“已核验 50／50 条”与“已复核 35／50 条”。“Continue review”跳回上次处理的条款。

### 3.2 Documents

上传区分为 Tender、Addenda／Clarifications、Bid 三组。文件列表显示文件名、类别、版本、页数和解析状态。

- **上传检查**：校验 PDF 格式、页数和可提取文本。本轮选中的招标、补遗和投标文件合计超过 100 页时提示调整；扫描页或文本提取失败的页面单独列出，可替换文件后重试。
- **补遗处理**：补遗上传后，系统列出被修改或新增的要求，用户确认后在要求清单中标注“Amended by Addendum N”，审查使用修改后的内容，原要求保留可查。
- **图纸登记**：从招标和补遗中的图纸目录提取图号、名称、修订号和日期，也可上传 CSV 补充或纠正。系统检查三类问题：图号重复、同一图号修订冲突、投标文件引用了已被替代的修订版本。检查结果作为审查结果进入工作台，分类为 Consistency。

### 3.3 Requirements

列表字段：条款编号、要求文本、类别、来源（文件与页码）、补遗标注、抽取出的约束（数值、单位、比较符、期限）。

用户可以纠正类别和约束字段、补充遗漏要求，或标记“不适用”。修改时保留原值，并要求填写理由。不适用的条款单独统计，不参与审查。

要求由系统从招标和补遗 PDF 中提取，同时支持导入已标注的要求文件（JSON 或 CSV），用于历史案例回放和演示。用户确认清单后启动审查。

### 3.4 Review Workspace

工作台是演示的核心页面，布局如下：

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ Project ▾ │ Round 2 │ Tender v1 · Addendum 1 · Bid v2 │ Reviewed 35/50    │
├─────────────┬──────────────────────────────┬─────────────────────────────┤
│ Clauses     │ TENDER  Addendum 1 · p.18    │ BID  Bid v2 · p.12  [1/2 ▸] │
│ [search   ] │ ┌──────────────────────────┐ │ ┌─────────────────────────┐ │
│ [filter  ▾] │ │                          │ │ │                         │ │
│ ✗ 2.1 Dura… │ │       page image         │ │ │       page image        │ │
│ ? 2.2 Bond… │ │                          │ │ │                         │ │
│ ✓ 2.3 ISO … │ └──────────────────────────┘ │ └─────────────────────────┘ │
│ ◂ prev next▸│ ◂ p.18 ▸   zoom ──○──        │ ◂ p.12 ▸   zoom ──○──       │
├─────────────┴──────────────────────────────┴─────────────────────────────┤
│ Field     │ Requirement      │ Bid response     │ Result                  │
│ Duration  │ ≤ 360 cal. days  │ 400 cal. days    │ ✗ Non-compliant         │
│ ▸ Reasoning chain: Classify → Retrieve → Extract → Rule                  │
│ [Confirm] [Correct] [Add evidence] [Mark N/A] [To remediation]  Note: __ │
└──────────────────────────────────────────────────────────────────────────┘
```

**条款导航**（左侧，可收起）：显示条款摘要、类别、系统判定和人工状态，支持搜索、按状态和类别筛选、上一条／下一条。

**双栏原文**（中部）：选中条款后，左栏跳到招标要求所在页（有补遗时默认显示补遗来源，可切换回原文），右栏跳到投标证据页。证据有多处时可在 `[1/2 ▸]` 之间切换。两栏各自翻页和缩放，不同步页码。引用一律显示文件、版本和 PDF 物理页码。

**核验面板**（底部）：

- **字段对照表**：要求值、投标实际值、判定。金额、日期、单位的换算由后端完成，表格中显示换算依据。
- **推理链**：Proposal 的“ML classifies → RAG finds the evidence → Rules verify”在此展开为四段，默认折叠：
  1. Classify：类别及所用模型；
  2. Retrieve：检索到的投标片段及来源页；
  3. Extract：LLM 抽取的结构化字段；
  4. Rule：触发的规则编号、规则版本、计算过程和结论。
- **人工操作**：确认、纠正字段（纠正后该条款立即按新字段重跑规则）、补充证据页、标记不适用、转入整改。每次操作记录操作人、时间和备注。

检索分数和分类概率只在推理链中作为技术信息显示，不作为合规可信度。

### 3.5 Remediation

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ Issues (6)        │ 2.1 Duration — Non-compliant                          │
│ ● 2.1 Duration    │ Requirement ≤ 360 days · Bid 400 days · Bid v2 p.12   │
│ ● 4.3 Insurance   ├──────────────────────────┬────────────────────────────┤
│ ○ 5.2 Drawing C-… │ Knowledge base           │ Revision draft             │
│                   │ ▸ Method stmt: Fast-track │ ┌────────────────────────┐ │
│                   │   programme (KB-012)      │ │ editable text          │ │
│                   │ ▸ Past bid: Project X §3  │ └────────────────────────┘ │
│                   │ [Use as reference]        │ Target: Bid v2 · §3.1      │
│                   │                           │ [Save draft]               │
├───────────────────┴──────────────────────────┴────────────────────────────┤
│ [Upload revised bid → Bid v3]          [Start re-inspection]              │
└──────────────────────────────────────────────────────────────────────────┘
```

每个整改项记录关联要求、问题说明、证据、知识库参考、修订草稿、目标文件位置和状态。

**知识库**：Proposal 写作 “Static Knowledge Base (KG)”，内容为标准施工方案和历史中标材料。本期实现为静态知识库，并维护“要求类别／关键词 → 材料”的关联表；整改页按关联关系推荐材料，每条建议显示来源和适用说明。如团队决定做成知识图谱，在此处增加关联图视图即可，其他页面不受影响。

**草稿**：系统依据所选参考材料生成修订草稿，用户可以编辑。草稿只作为参考文本，投标文件的实际修改由用户在原文件中完成。

**复检**：用户上传修改后的投标文件，生成新的投标版本后启动复检。复检针对新版本重新执行全部已确认的要求，生成新一轮审查，并按四类显示对比结果：已解决、仍存在、新出现、待确认。上一轮结果保留，可在顶部切换轮次查看。

### 3.6 Report

**合规矩阵**：条款编号、类别、要求及来源、系统判定、人工结论、投标证据（文件、版本、页码）、整改状态、审查轮次。

**未决项**：未复核条款、证据不足、未解决的不符合、解析失败页、不适用条款及理由。

**签核**：由 Manager 执行。签核条件为：本轮每条适用要求都已有人工处理（状态不是“未复核”）。仍不符合的问题可以保留，但会在报告中明确列出；签核表示审查结果已确认，不表示投标完全合规。签核记录签核人、时间、意见和审查轮次；签核后该轮只读，后续修改进入新一轮。

**导出**：合规矩阵 Excel（每个条款一行，含证据引用）；审查报告 PDF（概要、未决项、签核信息）。签核前也可导出，文件标注 DRAFT。

**评估视图（Should）**：支撑 Proposal 第 6 页的端到端验证。

- *Historical Case Replay*：导入已知问题清单（条款编号、预期结果），显示命中、漏报、误报，以及补遗修改是否被正确标出。
- *与人工审查对比*：系统自动记录每条条款从打开到人工处理的用时，汇总本轮审查总用时，与人工逐条审查的基线用时对比。

## 4. 状态规则

| 维度 | 状态 | 说明 |
| --- | --- | --- |
| 任务 | Processing、Done、Failed | 解析、提取、审查等后台任务 |
| 系统判定 | Compliant、Non-compliant、Insufficient evidence | 由证据和规则得出 |
| 人工状态 | Unreviewed、Confirmed、To remediate、To re-inspect、Closed | 审阅与整改流程 |
| 报告 | Draft、Signed | 绑定某一审查轮次 |

状态规则：

- 系统判定与人工结论分开保存，人工纠正不覆盖系统原始结果。
- 证据未找到、页面无法解析、要求有歧义时，判定为 Insufficient evidence 并转人工处理，不判为 Non-compliant。完整解析后确认必备文件缺失，可以由规则判定 Non-compliant。
- 整改项只保存草稿时保持 To remediate；上传新投标版本后变为 To re-inspect；复检通过并经人工确认后变为 Closed。
- 标记不适用是一种人工处理，必须填写理由，并在报告中单独统计。

长任务显示实际阶段和计数，例如“Parsed 80/100 pages”“Checked 35/50 clauses”。刷新页面或切换页面不会重新触发推理；失败时给出重试或替换文件的入口。

## 5. 视觉与阅读体验

以桌面端为主。浅灰背景、白色阅读区、深蓝主操作色；红色表示不符合，琥珀色表示证据不足或待确认，绿色表示符合；每个状态同时配文字或图标，不只靠颜色区分。

屏幕空间优先留给条款、字段对照和原文页面。长文本可以展开，金额和单位对齐，文件名和版本始终可见。模型配置和详细日志放在推理链或技术详情中，用户不需要了解模型实现也能完成审查。

## 6. 数据与保密

Proposal 将 LLM 幻觉和保密列为关键风险，界面相应处理：

- **幻觉**：每个结论必须对应可点击的原文页；没有证据时显示 Insufficient evidence，不生成合规描述。知识库建议必须标出处。
- **外发提示**：上传页和设置中显示当前使用的 LLM 服务，并说明哪些文本会发送到外部服务。
- **项目隔离**：每个项目的文件和结果分开存储，提供删除整个项目数据的操作。

## 7. 技术实现约定

**职责划分**：前端负责文件选择、原文定位、筛选、人工输入、状态展示和流程操作。后端负责解析、要求提取、分类、检索、抽取、规则执行、复检对比、持久化和导出。

**Streamlit 约定**：

- 用 Streamlit 多页面应用实现六个页面，项目、轮次、筛选条件和当前条款统一保存在 `st.session_state`。
- 原文显示：后端把 PDF 页面渲染为图片并缓存，前端用图片显示，配合翻页和缩放控件。不嵌入浏览器 PDF 阅读器，以免被浏览器拦截。
- 长任务在后台执行，状态和结果写入持久化存储（如 SQLite 加项目文件目录）；页面定时读取进度。页面重跑只读取结果，不启动推理。
- 演示可以使用已缓存的审查结果，需在界面上标明对应的文件版本和审查轮次。

**核心数据对象**：

| 对象 | 最少需要的信息 |
| --- | --- |
| 项目 | 标识、名称、当前轮次 |
| 文档版本 | 标识、类别、版本号、文件位置、页数、解析状态、替代关系 |
| 图纸登记 | 图号、名称、修订号、日期、来源文档、检查结果 |
| 要求 | 标识、原文、类别、来源页、补遗标注、约束字段、适用性 |
| 证据 | 文档版本、物理页码、片段内容 |
| 审查轮次 | 使用的文档版本、要求清单、规则版本、任务状态 |
| 审查结果 | 系统判定、证据、推理链、人工状态、操作记录 |
| 整改项 | 关联要求、问题、知识库参考、草稿、目标版本、复检结果 |
| 知识库材料 | 标识、标题、类型、内容、关联类别／关键词 |
| 签核 | 审查轮次、签核人、时间、意见、导出文件 |

## 8. 排期与验收

Proposal 原定 CP4 代码冻结为 10-18，本方案将功能冻结调整为 10-23，留出视频和报告的时间。

| 日期 | 工作内容 |
| --- | --- |
| 10-19（一） | 方案定稿；页面骨架、数据对象、持久化 |
| 10-20 – 10-21 | Documents、Requirements、Review Workspace |
| 10-22 | Remediation、知识库、复检对比；图纸登记检查 |
| 10-23 | Report、签核、导出；评估视图（Should）；全流程联调，**功能冻结** |
| 10-24 | 录制两段 5 分钟视频，完成报告 |
| 10-25 | 缓冲；23:59 前提交 |

10-22 结束时如果 Must 项未完成，评估视图顺延或删除，不占用 10-24 的视频和报告时间。

**界面验收场景**：

| 场景 | 通过条件 |
| --- | --- |
| 文档包输入 | 英文可搜索 PDF 在 100 页内完成上传与解析；超限和失败页有明确提示 |
| 要求与补遗 | 要求可定位到来源页；补遗修改被标注，审查使用修改后的内容 |
| 图纸检查 | 重复图号、修订冲突、引用旧修订均能被列出并定位 |
| 证据审阅 | 两栏定位到正确的文件、版本和物理页；多处证据可切换 |
| 规则核验 | 数值、单位、期限的对照表和推理链可查看，结果与预设测试用例一致 |
| 歧义处理 | 证据缺失、解析失败进入 Insufficient evidence，不被判为合规或不合规 |
| 人工复核 | 确认与纠正保存原值、理由、操作人和时间 |
| 整改复检 | 知识库建议有出处，草稿可编辑，新版本复检后显示四类对比 |
| 签核导出 | 草稿标注 DRAFT；签核后的导出包含人工结论、证据引用、版本和签核信息 |
| 任务稳定 | 刷新和切页不丢失进度，不重复启动同一任务 |

**与 Proposal 评估计划的对应**：

| Proposal 评估项 | 呈现位置 |
| --- | --- |
| Clause Classification：Precision、Recall、Macro F1 | 技术报告 |
| Evidence Retrieval：Top-k Passage Recall | 技术报告 |
| Rule Verification：约束测试用例 | 技术报告；工作台推理链演示 |
