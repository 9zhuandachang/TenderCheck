# TenderCheck — Atomic Requirement Annotation Guideline

## 1. 任务定义和输入范围

从纳入范围的文件中识别 **Atomic Bid-Reviewable Requirements**：即原文规定投标人在投标阶段应具备、提交、声明、承诺、响应，或能够影响评分的独立要求。这里的“Bid-reviewable”仅用于**界定应标注哪些文本**，不是要求标注员检查某份 Bid 是否合格。

**本轮纳入**：招标文件正文、招标公告、答疑／补遗／澄清文件。若公告是正文内同一内容的完整副本，不因额外上传副本而重复标注；但不同原文位置独立出现的规定保留。

**本轮不纳入**：独立工程量清单／控制价文件、设计与勘察附件。这些交由独立数据处理流程。**不能据此跳过招标文件正文中出现的报价规则、工程量清单填写规则、技术响应要求或补疑中的明确投标要求。** 补疑里的纯设计参数纠错、清单数据修正不机械改写为训练用 Atomic Requirement。

对每条提取内容输出五列：`ID | Page | Section | Requirement Type | Requirement`。只输出正样本；保留原文出现位置上的重复；不对条款作优先级判断、版本覆盖或语义去重。

## 2. 唯一允许的八类标签

| Requirement Type | 标注对象 | 示例 |
|---|---|---|
| Qualification | 企业／人员资格、证书、经验、信誉、劳动关系、投标准入 | 项目经理须具备一级注册建造师资格。 |
| Document | 当前投标文件应提交的文件、证明、承诺、附件、签署和格式 | 投标文件须附项目经理身份证扫描件。 |
| Technical | 当前投标技术响应的方案内容、技术措施、参数、质量技术要求 | 施工组织设计须提出混凝土温控防裂措施。 |
| Commercial | 投标报价、费用、税费、保证金、计价方式、金额比例 | 安全措施费不得低于规定计价基数的 2%。 |
| Schedule | 投标工期、进度、关键节点、投标有效期 | 投标工期须为 540 日历天。 |
| Consistency | 同一投标包内、与招标数据或证明材料之间明确规定的一致性 | 报价总价应与项目总价表合计一致。 |
| Integrity | 投标材料的真实、不得伪造、隐瞒、挂靠 | 不得提交虚假业绩证明。 |
| Scoring | 非强制性得分条件、档位、技术评分标准、加分机会 | 每增加一项符合条件的业绩得 2 分，最高 4 分。 |

**分类规则**：每条只能有一个 Type。按原文独立要求的核心内容分类，而非按章节分类。`有资格` → Qualification；`提交资格证` → Document；`证书信息一致` → Consistency；`不得伪造证书` → Integrity。纯得分条件 → Scoring；为申报加分必须提交证明 → Document。Scoring 只表示评分规则性质，不要求标注员计算分数。


## 3. INCLUDE — 应提取

1. 当前投标阶段明确要求的资格、人员、业绩、信誉、联合体限制。
2. 当前投标文件须提交、填写、签署、声明、承诺的文件与内容。
3. 投标方案须回应的技术、质量、工期、报价和投标有效期要求。
4. 投标报价组成、金额、比例、限价、保证金及正文中的 BOQ 填写／跨表规则。
5. 评分标准中明确规定的得分条件、档位、上限及评分质量要求。
6. 条件性投标要求（如采用保函、如拟分包、如申报评分），须保留触发条件。
7. 原文中通过标题、表格字段、注释、清单项共同表达的实质要求，即使没有“必须／应”。

## 4. EXCLUDE — 不提取

1. 纯项目背景、地址、联系人、资金来源、介绍性文字。
2. 仅约束中标后实际施工、保修、验收、合同争议等未来履约行为；但**当前明确要求提交的履约承诺书、技术方案或报价**要标注其当前提交／报价要求。
3. 平台登录、文件下载、上传、加密解密、现场签到、递交截止等操作性流程；可在投标文件本身识别的签字盖章／附件要求不因此排除。
4. 需要比较不同竞争投标人才能判断的串标／异常相似要求；同一投标包内部明确的一致性要求保留。
5. 招标人、评委、监理人的程序行为、纯评标基准价计算过程、澄清操作流程。
6. 明确不适用的通用模板，及仅供参考的方案目录。
7. 只有“见某附录／参照某标准”而无新增实质条件的纯引用；到实际出现条件的位置标注，不自行补充未提供的标准内容。
8. 独立 BOQ／控制价和设计／勘察附件的普通结构化记录（本轮文件范围排除）。

## 5. Atomic Decomposition — 拆分与保真

**原则**：一条输出表达一个语义上独立的标注目标；可独立判断是否具备／是否提交／是否符合规定的条件，通常拆开。例：“项目经理须具备一级建造师、B 类证、类似业绩”拆三条。不要把“完整的安全体系包含组织、制度和目标”机械按名词拆三条，除非原文独立列出检查／评分要求。

**AND / OR**：AND 中独立要求拆开。OR 选项不能改写成多个同时必需的条件；可保留为一条完整的“满足下列条件之一……”要求。只有在各选项能独立表达且保留替代逻辑时才拆。五列无法无损表达的复杂嵌套条件，优先保留完整逻辑，不为追求条数强拆。

**条件和例外**：`如采用银行保函，应提交扫描件` 不得改为 `必须提交银行保函`。保留地域、金额、时间、单位、比例、计价基数、最高分、例外及限定范围。

**规范化**：可以将标题＋数值改写成完整句，可以补充原文上下文中明确的主语，不得凭常识添加约束。原文跨页时 `Page` 用要求起始 PDF 物理页。不同位置的同义要求保留；同一位置不要生成多个纯改写副本。

## 6. 按章节的详细标注指引

以下章节是**阅读重点**，不等于凭章节名称决定是否纳入。不同项目的章节编号、名称可能不同，应按实际文本执行。

### 6.1 第一章：招标公告

**重点提取**：
- 投标人资质等级、法人资格、营业资格；企业类似业绩的时间窗口、金额／规模、工程类型。
- 项目经理／技术负责人资格、执业证书、安全证、业绩、岗位限制。
- 信誉／信用／不良记录的具体准入条件；若原文是多条独立限制则拆，若是互斥的替代合格路径则保留 OR 逻辑。
- 是否接受联合体、投标保证金金额与允许形式、明确要求投标响应的工期或质量。

**通常不提取**：招标人地址电话、获取文件方式、网站注册、上传和开标操作。项目概况中的地理位置／规模不自动标成 Requirement，除非原文明确将其作为投标响应约束。

**重复处理**：公告若在正文中原样重印，且是同一份公告的重复文件副本，不因为附件副本再建一套标注；正文其他章节重新规定的资格要求则保留其独立来源记录。

### 6.2 第二章：投标人须知及前附表／资格附录

这是**高密度标注章节**，必须逐条检查前附表、正文、资格附录和备注：
- **资格**：企业资质、营业执照、安全生产许可证、人员职称／注册资格／安全证、人员数量、类似项目业绩、信用记录、证书有效性、社保和本单位人员认定。
- **证据材料**：网页截图、合同、完工证明、身份证、社保、授权委托、承诺书。`须具备资格` 与 `须提供资格证明` 分开标注。
- **投标文件组成**：投标函、附录、资格审查资料、施工组织设计、已标价清单、项目管理机构、各类承诺。
- **报价／保证金**：金额、币种、计价税率、最高限价、报价费用组成、允许的保证金形式、当前文件要求的证明。
- **期限与技术响应**：投标有效期、工期、质量、招标范围、技术标准的实质响应要求。
- **分包**：只有投标阶段需申报的拟分包信息、资质或证明才提取；未来分包审批和现场管理不提取。
- **禁止情形**：独立法人、关联机构限制、信用惩戒、人员在建限制、虚假资料等，按原文独立条款提取；不把跨竞争投标人的比较纳入。

**特殊边界**：前附表和通用正文若各自有实质规定，按出现位置忠实记录，不替招标方裁定优先级；若正文只是“见前附表”，不为纯引用新造一条。电子平台操作、解密、下载和递交流程不提取；投标文件本身的签署要求可以提取。

### 6.3 第三章：评标办法

按**初步评审、响应性评审、详细评分**分别阅读：
- **形式评审**：名称与证照一致、签章、格式、证明材料相符等 → Consistency / Document / Integrity。
- **资格评审**：资质、业绩、信誉、人员资格等 → Qualification；即使第二章已有同义条款，独立位置重复仍保留。
- **响应性评审**：投标范围、工期、质量、有效期、保证金、报价上限、BOQ 规则等 → 按语义分配 Schedule / Technical / Commercial / Consistency / Document。
- **报价否决／数值要求**：最高限价、明确比例区间、安全措施费最低金额、清单金额关系 → Commercial / Consistency；保留比较符号、上下限、计算基数。
- **商务评分**：类似业绩每项分值、奖项、信用等级、市场行为、项目经理／技术负责人评分业绩 → Scoring；提交奖项证书或网页截图的独立要求 → Document。
- **技术评分**：施工方案、质量、安全、环保、导流、度汛、冬雨季、施工进度、平面布置等评分档位 → Scoring；不因为出现“无方案得 0 分”就把该评分项自动改成强制 Document。

**通常排除**：评委抽取、评标基准价计算步骤、评委如何打分／汇总／推荐候选人、澄清通知等纯评审程序。注意：原文直接规定评分条件的公式可以保留为 Scoring；纯评委内部计算程序不提取。

### 6.4 第四章：合同条款及合同附件

这是**最容易过度提取的章节**。不得因为“承包人应／不得”就提取全部合同义务。

**只重点查找明确指向当前投标内容的条款**：
- `投标报价应包含……费用`、`已标价工程量清单应计入……` 等当前报价组成 → Commercial。
- `投标文件须提交……承诺书／方案` → Document；当前投标技术方案中必须写明的措施 → Technical。
- `投标时选择……品牌／技术时应满足……` 等明确当前响应条件 → Technical。

**通常排除**：中标后驻场天数、工资发放、现场检查、分包审批、竣工验收、缺陷修复、合同争议、履约保函等仅发生在合同执行期的行为。即使将来企业数据库可能查到相关信息，也不因此纳入。

**合同附件**：合同协议书、履约担保、预付款担保等格式存在本身不等于投标时必交；若其他条款明确要求当前 Bid 附某承诺或表格，才标注提交义务。

### 6.5 第五章：工程量清单说明（仅限招标文件正文内的文本）

**重要范围说明**：本轮**不标注独立《工程量清单／控制价》文件**，但招标文件正文第五章的自然语言报价说明仍需提取。

**重点提取**：
- 必须提供的报价表类型（确为本项目适用时）；单价、合价必填；币种和税费要求。
- 不得擅自更改清单项目；编码、名称、单位、工程数量应与招标清单一致的**通用规则**。
- 投标总价与总价表、分类分项表、费率表、材料／机械／人工单价表的**跨表一致性规则**。
- 安全措施费、暂列金额、暂估价、代理费、模板费、临时工程费等报价组成及明确比例／金额要求。
- 单价分析表、费用分析书、按条件提交的辅助表格。

**不提取**：`投标人应认真核对` 这种无法从当前投标材料体现的纯动作；空白模板每个普通单元格；把每个 BOQ 子目编码／名称／数量重复改写为一条自然语言要求。普通子目行属于独立结构化数据流程。

**拆分示例**：`清单编码、单位、数量与招标清单一致` 可按独立字段拆为三条通用 Consistency 规则，但**绝不对每个子目重复实例化这三条规则**。

### 6.6 第六章：图纸

若本轮仅收到正文中的图纸目录、引用或“另册提供”说明，不生成想象中的技术要求。**独立设计／勘察图纸附件本轮不做 ML 标注**。但正文其他章节明确写出的投标技术响应要求仍应按原位置标注。

### 6.7 第七章：技术标准和要求

**重点提取**：正文明确要求当前投标技术方案响应的性能指标、材料等级、施工方法、技术措施、质量标准、特殊参数，以及投标阶段必须说明的技术内容。

**排除**：只有“参照某标准文件”但标准未提供时，不自行展开；纯未来施工执行细节且没有当前投标响应义务时，不自动提取。章节标题叫“技术标准”不代表每句话都要标注；若正文仅有引用说明，可能为 0 条。

### 6.8 第八章：投标文件格式

这是**Document 要求密集章节**，应特别关注模板中的正文注释、填写说明和“应附／须提供”：
- **投标函／附录**：工期、质量、有效期、项目经理／技术负责人等当前应填写或承诺的内容；签章、基本账户信息。
- **身份证明／授权委托**：身份证扫描件、授权期限、委托代理人社保、签署格式，保留条件。
- **保证金**：按转账、电汇、保函、保险等适用路径分别提取证明材料及文件要求，不把替代形式都改成必交。
- **项目管理机构**：人员组成表、简历、身份证、资格证、社保证明、业绩截图、项目经理承诺书等。
- **资格审查**：营业执照、资质、安全许可证、类似业绩及其证明；本项目明确“不要求”的财务表等通用模板不标为必交。
- **报价文件**：报价函、已标价清单的提交与格式、商务／报价文件中明确要求保持一致的字段。
- **施工组织设计**：正文明确“应”包含的质量、安全、进度、环保、度汛、导流、混凝土质量等方案和技术措施；对具体技术内容用 Technical，对提交文件本身用 Document。
- **技术附表**：明确“应附”的设备表、检测仪器表、劳动力计划表、进度网络图、施工总平面图、临时用地表分别标注。

**通常排除**：仅供参考的施工组织设计目录，未明确要求提交的普通模板字段，当前项目不适用的联合体协议、财务模板等。`有表格` 不自动等于 `必须提交`。

### 6.9 答疑／补遗／澄清（跨章节附加来源）

这些文件属于**本轮标注输入**。按同一八类标准提取其中明确新增或重述的投标资格、文件、报价、评分及当前技术响应要求。Q&A 中只有问题、没有可确认的回答时不据问题自行生成要求。

**不要在标注任务中做版本裁定**：补疑与原文件有不同实质性规定时，各自原文位置照实标注；不自动删除旧记录，不推断哪条法律上有效。`原图纸作废／设计尺寸纠正／清单普通数量修改` 这类纯版本或结构化参数信息，不机械生成 ML Atomic Requirements，交由单独处理流程。

## 7. 来源、重复、编号

- 同一原文位置不要创建多个语义完全相同的改写副本；不同原文位置的实质重复保留。
- `Page` 使用对应**源 PDF 的物理页码**（第一页为 1），`Section` 使用原文编号／标题；多个文件可在 Section 前缀标注文件名，例如 `招标公告.pdf / 四、投标资格`，避免不同 PDF 页码混淆。
- `ID` 按纳入范围文件的约定顺序及各文件内出现顺序连续编号 `T0001`、`T0002`……；文件处理顺序在同一批次开始前固定，不能因内容相似自行调整。
- 原文与规范化要求之间的对应关系可保存在内部工作记录，但最终主表严格五列。

## 8. 标注流程与质量检查

1. 确认输入文件是否属于本轮范围；按文件与页码顺序阅读所有可访问文本、标题、表格及注释。
2. 识别符合 INCLUDE 且不触发 EXCLUDE 的内容，进行最小必要规范化与原子拆分。
3. 分配唯一的八类 Type，保留条件、OR 逻辑、数值、例外、评分档位。
4. 回到原文逐条核对：是否确有该要求、是否忠实、Type／Page／Section 是否正确。
5. 再检查尚未提取的原文，寻找漏标。逐页阅读和复核属于**标注质量控制**，不等于执行 Bid 合规审查。
6. 检查五列完整、ID 连续、标签合法、页码顺序、无凭空新增、跨位置重复保留。

不要求 Agent 判断投标人的 PASS／FAIL／N/A，不查询企业数据库，不计算真实得分，不判断合同条款法律效力，也不输出合规矩阵。

## 9. 输出格式

主要交付 `annotations.json`，顶层为数组，每条对象**恰好五个键**：

```json
[
  {
    "ID": "T0001",
    "Page": 4,
    "Section": "3.1 投标人资格要求",
    "Requirement Type": "Qualification",
    "Requirement": "投标人须具有水利水电工程施工总承包一级及以上资质。"
  }
]
```
